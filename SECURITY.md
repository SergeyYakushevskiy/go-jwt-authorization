# Политика безопасности

## Общие положения
Проект разработан в познавательных и образовательных целях для изучения:

* механизмов аутентификации пользователей с использованием JWT;
* разграничения доступа на уровне HTTP-запросов;
* принципов работы access и refresh токенов;
* механизмов отзыва токенов;
* разработки серверных приложений на языке Go.

## Обрабатываемые данные
Проект предусматривает хранение следующих данных пользователей:

* фамилия;
* имя;
* отчество;
* логин;
* пароль.

Аутентификационные данные надёжно хранятся в базе данных.

## Модель безопасности
Основным механизмом аутентификации проекта является JSON Web Token (JWT). Аутентификация осуществляется посредством HTTP-запросов с передачей токена в заголовке:

`Authorization: Bearer <token>`

Проект реализует механизм разделения срока действия токенов на:

* access токен — используется для выполнения авторизованных запросов;
* refresh токен — используется для получения нового access token.
Каждый токен имеет ограниченный срок действия.
Проект не реализует самостоятельную модель разграничения доступа.

## Защита криптографических ключей
Для работы криптографических механизмов используется мастер-пароль. Мастер-пароль не хранится в репозитории исходного кода и не включается в состав файлов проекта. На эксплуатационном сервере мастер-пароль хранится отдельно от Git-репозитория и исходного кода.

Мастер-пароль основан на криптографическом механизме ГОСТ Р 34.11-2012 с размером ключа 256 бит.

Исходный код проекта не должен содержать значения мастер-пароля, криптографических ключей и иных секретных параметров.

## JWT
Для JWT используются криптографические механизмы на основе HS256 в соответствии с конфигурацией проекта.

При обработке JWT сервер должен:

1. проверить корректность структуры токена;
2. проверить криптографическую подпись;
3. проверить срок действия токена;
4. определить тип используемого токена;
5. проверить идентификатор jti;
6. отклонить токен, находящийся в списке отозванных токенов.

Данные, содержащиеся в JWT, не должны рассматриваться как достоверные до успешного прохождения криптографической проверки токена.

## Отзыв токенов
Для идентификации отдельных экземпляров JWT используется параметр jti (JWT ID). Проект предусматривает список отозванных идентификаторов jti. При поступлении авторизованного HTTP-запроса сервер проверяет наличие jti токена в списке отозванных токенов. Если идентификатор обнаружен в списке отзыва, запрос отклоняется независимо от того, является ли криптографическая подпись токена корректной. Данный механизм позволяет прекратить действие ранее выданного токена до истечения его штатного срока действия.

## HTTP-аутентификация
Для передачи access token используется стандартный HTTP-заголовок:
Authorization: Bearer <token>

Сервер не должен принимать JWT из не предусмотренных проектом источников.

При отсутствии токена, нарушении его структуры, истечении срока действия, некорректной подписи либо нахождении `jti` в списке отозванных токенов запрос считается неаутентифицированным.

## Сетевое взаимодействие
Проект оформлен с учётом архитектуры Клиент-Сервер. В качестве протокола сетевого взаимодействия был выбран HTTP. Для обеспечения должного уровня защиты секретов при использовании проекта в реальной информационной системе передача токенов должна осуществляться по защищённому каналу связи с использованием HTTPS/TLS.

## Ограничения проекта
Проект имеет учебное назначение и не позиционируется как универсальная промышленная система управления доступом. В частности, проект не ставит целью реализацию:

* сложной модели ролей и разрешений;
* многофакторной аутентификации;
* централизованного управления идентификацией;
* единой системы управления секретами;
* специализированной инфраструктуры управления криптографическими ключами;
* комплексной защиты от всех классов сетевых атак.

## Ответственность за безопасность
Безопасность проекта зависит не только от реализации JWT, но и от способа его развёртывания и эксплуатации. При использовании проекта необходимо обеспечить защиту:

* мастер-пароля;
* криптографических ключей;
* базы данных пользователей;
* списка отозванных токенов;
* серверной инфраструктуры;
* каналов передачи данных.
